# Martin Brain's Subpolynomial-Encoding Benchmarks

## Source

<https://github.com/martin-cs/subpolynomial-encoding/tree/main/benchmarks>

Two seed archives `seed-23.tar.xz` (2474 benchmarks) and `seed-42.tar.xz`
(1024 benchmarks). Generated by Martin's
`subpolynomial_experiment_generator` to investigate properties of
the subpolynomial encoding of polynomials over $\mathbb{Z}_{2^d}$.

## Benchmark structure

Random polynomials $p(x)$ of various degrees (2-53) over various
bitwidths (8, 16, 32, 64). The **README warns**: random polynomials
are used (not random *permutation* polynomials), so some benchmarks
are unexpectedly UNSAT.

Categories (from filenames):

- `addition` — checks $p(x) + q(x) = (p+q)(x)$ as polynomial identity.
- `multiplication` — checks $p(x) \cdot q(x) = (pq)(x)$.
- `correctness` — checks two encodings (native vs subpolynomial,
  original vs reduced) are equivalent.
- `equality` — checks $p(x) = c$ has a solution.
- `nonequality` — checks $p(x) \neq c$ has a solution.
- `bounding` — checks degree bounds.
- `identity-point` — checks $p(x_0) = c$ for a specific $x_0$.
- `root-finding` — checks $p(x) = 0$ has a root.

Each instance comes in two encodings (native vs subpolynomial) and
two reductions (original vs reduced).

## Experimental setup

210 benchmarks, stratified random sample across both seeds and all
categories present per seed (5 per category per seed). Five
configurations:

| Config        | Description                                      |
|---------------|--------------------------------------------------|
| `shift_add`   | Pure bit-blasting, shift-add multiplier, no simplification, no algebraic |
| `comba_cs`    | Pure bit-blasting, Comba/CSE multiplier, no simplification, no algebraic |
| `pair_detect` | Bit-blasting + Paper 1's `--refine-arithmetic` pair detection (no algebraic) |
| `p2_algebraic`| Paper 2's full algebraic layer (Gröbner + ZFP test) over Comba/CS bit-blast |
| `all_combined`| Algebraic + pair detection (Paper 1 + Paper 2)   |

10 second timeout per cell.

### Algebraic-only wins (only Paper 2 solves)

**18 benchmarks** that no bit-blasting configuration can solve within
10 s, but the algebraic layer dispatches in seconds. Examples:

- `bitwidth-16-degree-20-seed-23-multiplication-original-native-encoding`:
  `p2_algebraic` 1.15 s, all bit-blasting T/O.
- `bitwidth-32-degree-22-seed-23-multiplication-original-native-encoding`:
  `p2_algebraic` 5.75 s, all bit-blasting T/O.
- `bitwidth-16-degree-22-seed-23-addition-original-native-encoding`:
  `p2_algebraic` 1.48 s, all bit-blasting T/O.

These are exactly the polynomial-identity benchmarks Paper 2 is
designed for: the Gröbner basis recognises the polynomial equality
and dispatches in time linear in the polynomial size, rather than
exponential in the bitwidth.

### Bit-blast-only wins (algebraic T/Os)

**8 benchmarks**, all in `equality` and `nonequality` categories.
These ask "does $p(x) = c$ have a solution?" — a SAT-finding
question that the Rabinowitsch-augmented Gröbner basis is poorly
suited to. The algebraic layer attempts to disprove the existence
of a root via ideal membership, which is the wrong reasoning
direction. Bit-blasting handles SAT-finding directly.

### Performance on commonly-solved benchmarks

On the 100 benchmarks all five configs solve:

```
shift_add:    124.62 s
comba_cs:     124.91 s
pair_detect:   97.67 s   <-- 22% faster than shift_add
p2_algebraic: 125.06 s
all_combined:  99.08 s
```

`pair_detect` and `all_combined` are noticeably faster on the
common-solve set, indicating Paper 1's pair detection helps when
it doesn't hang. The 8 benchmarks where pair detection causes
hangs (the regression observed above) bring its solved count
down to 109.

### Pair-detect refinement-loop regressions

Three benchmarks where bit-blasting solves in <1 s but pair
detection T/Os:

- `bitwidth-8-degree-5-seed-23-addition-original-native-encoding`:
  shift_add 0.11 s; pair_detect T/O.
- `bitwidth-8-degree-8-seed-23-addition-original-native-encoding`:
  shift_add 0.22 s; pair_detect T/O.
- `bitwidth-8-degree-12-seed-23-addition-original-native-encoding`:
  shift_add 0.56 s; pair_detect T/O.

These are Paper 1 issues, not Paper 2 issues. The refinement loop
appears to oscillate; needs investigation but is out of scope for
the current Paper 2 work.

## Headline numbers for Paper 2

On Martin's 210-benchmark stratified sample:

- **Paper 2 alone solves 127/210 (60%)**, the best single
  configuration.
- **18 benchmarks solved only by the algebraic layer** that no
  bit-blasting variant can solve within 10 s.
- On polynomial-identity categories (addition, multiplication,
  correctness): Paper 2 solves **33/70**, bit-blasting solves only
  **15/70** — a **2.2× improvement**.
- On SAT-finding categories (equality, nonequality): Paper 2 solves
  23/60, bit-blasting solves 39/60. The algebraic layer is strictly
  weaker here, as expected.

## Reproducibility

```bash
# Clone Martin's benchmarks
mkdir -p /tmp/martin-bench
cd /tmp
git clone --depth 1 https://github.com/martin-cs/subpolynomial-encoding.git
cd /tmp/martin-bench
tar -xJf /tmp/subpolynomial-encoding/benchmarks/seed-23.tar.xz
tar -xJf /tmp/subpolynomial-encoding/benchmarks/seed-42.tar.xz

# Run comparison
cd <cbmc-github>
ulimit -v 57591731
timeout 7800 bash bench-multiplication/run-martin-subpoly-v2.sh
```

Note: Random sampling means re-runs will produce different exact
benchmarks but should preserve overall trends.

## Implications for the paper

1. **§4 Evaluation**: Add a paragraph (or sub-section) using these
   numbers to demonstrate that Paper 2's algebraic layer scales to
   high-degree polynomial identities (degree up to 32 on 16-bit, up
   to 22 on 32-bit) that bit-blasting cannot handle within practical
   timeouts.

2. **§5 Discussion / Limitations**: Be explicit that the algebraic
   layer is *strictly weaker* on SAT-finding queries
   (`equality`, `nonequality`). This is a known property of the
   Rabinowitsch trick — it's a UNSAT-detection technique. Paper 2
   already orchestrates the layered fallback (algebraic first, then
   bit-blast if inconclusive), so in practice a user gets the union
   136/210, not just 127.

3. **Future work**: The 8 SAT-finding losses suggest a research
   direction: *can we construct partial models from a non-trivial
   Gröbner basis*? Currently we extract candidate values for some
   variables, but not enough to dispatch SAT-finding queries
   directly.
