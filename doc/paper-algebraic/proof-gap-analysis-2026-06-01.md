# Why did we have soundness proofs yet still ship soundness bugs?

Date: 2026-06-01. This addresses the central concern raised after
the Item 12/13/14 findings: the project has a substantial Lean
soundness development (65 traceability entries, zero `sorry`),
yet the ablation audit found the algebraic pre-solver wrongly
reporting `unsat`/SUCCESSFUL on ~41 real benchmarks.

**Short answer**: the proofs are correct. They verify the
*algorithm core* and the *equality* encoding. Both bugs live in
steps that were **outside the verified boundary** — one in a
*documented-but-unenforced assumption*, one in an
*entirely-unmodelled encoding step*. The traceability audit gave
false confidence because it checked that every `// PROOF:`
reference resolves to a real theorem, but never checked that
every soundness-critical step *has* a `// PROOF:` reference.

This is a classic and generalizable failure mode of
"proof-carrying" implementations: **the dangerous gap is not a
wrong proof, it is a load-bearing step that nobody annotated, so
the audit could not see it was missing.**

## What is actually proven (and is correct)

1. `Encoding.lean::toPolynomial_eval` — the expression encoder is
   faithful for `const, var, +, -, *, neg, cast, zext,
   extract_low` **at a single fixed width `d`**:
   `eval env e = eval env (toPolynomial e)` in `ZMod (2^d)`.
2. `Encoding.lean::encodeEquations_satisfiable_iff` — a system of
   **equalities** is satisfiable iff the encoded polynomial
   system is.
3. `GroebnerSoundness.lean::soundness_of_odd_constant_check` — the
   engine is sound: if an **odd constant** lies in the ideal
   generated by the input polynomials `F`, then `⟨F⟩ = ⊤`, so the
   polynomial system `F = 0` has **no solution** over `ZMod(2^d)`.
   Plus the ideal-preservation lemmas (S-polynomials, reduction,
   the 2-trick) that justify the Gröbner engine.

All of this is true and well-mechanised. The Gröbner engine, the
2-trick, and the equality encoding are sound.

## Bug A — a documented assumption the code did not enforce

The Lean model `BVExpr d n` is parameterised by **one width `d`**.
Its `cast` constructor is `BVExpr d n → BVExpr d n` (same `d`) and
evaluates as the identity. The model **cannot even represent** a
width-changing cast. The C++ encoder documents this exactly
(`poly_extract.cpp`):

> ASSUMES: variable widths are consistent throughout the
> polynomial system; cast operators do not change the OUTER
> bitwidth at which the polynomial is evaluated.
> MAINTAINED BY: set_bitwidth() … accepting only equal or wider
> source types ("return bw >= bitwidth").

The "MAINTAINED BY" clause is wrong: `return bw >= bitwidth`
*accepts* a wider type and then **silently keeps the narrower
ring** (it does not update `bitwidth`). So a 32-bit promotion of a
9-bit truncated product (`assoc.c`) is absorbed into the 9-bit
ring — precisely the situation the ASSUMES clause forbids. The
proof's hypothesis was stated but **not enforced** by the code it
claimed to be maintained by.

> Lesson: an `ASSUMES` clause is only as good as the code that
> enforces it. Here the enforcement was a one-line predicate that
> did the opposite of what the comment claimed.

## Bug B — an encoding step that was never modelled at all

To refute a disequality `diff ≠ 0`, the implementation adds the
polynomial `diff·e − 1` to the system (Rabinowitsch). This step:

- has **no `// PROOF:` annotation** in `boolbv.cpp` (the three
  sites `__rabinowitsch`, `__rab`, `__rab_disj` are unannotated);
- has **no row in `TRACEABILITY.md`** (the only disequality rows
  cover *recognising* `bvult 0 x ⇒ x≠0`, not *encoding* `x≠0`
  into a polynomial);
- is **not in the `BVExpr` model** — there is no disequality
  constructor and no `e`-variable in `Encoding.lean`.

And it is **mathematically false over `ZMod(2^d)`**: `diff·e = 1`
asserts `diff` is a *unit*, but over `ZMod(2^d)` non-zero ≠ unit
(e.g. 16 is non-zero, non-invertible mod 256). So
`UNSAT(F ∪ {diff·e−1}) ⇏ UNSAT(F ∪ {diff≠0})`.

The most striking part: `GroebnerSoundness.lean` **contains the
fact that would have caught this** —
`ZMod.two_not_isUnit` ("2 is a non-unit in `ZMod(2^d)`") — but it
is labelled *"needed for the **incompleteness** direction"*. The
author saw the unit issue and filed it under "we might fail to
prove some true things" (incompleteness, harmless), not "we might
prove some false things" (unsoundness, fatal). The soundness
bridge that *would* have forced an `IsUnit diff` hypothesis —
"`Rabinowitsch-UNSAT ⇒ original-disequality-UNSAT`" — was simply
never stated as a theorem. Lemma 3a
(`exists_mul_eq_one_of_isUnit'`) proves the *converse* direction
(`IsUnit d → ∃e, d·e=1`) and carries the `IsUnit` hypothesis, so
the hypothesis existed in the proof library but was never wired
into a soundness obligation on the refutation path.

## Why the traceability audit did not flag it

The earlier "bi-directional traceability audit" verified:

- **forward**: every `// PROOF:` ref in `src/` resolves to a
  theorem of that name; and
- **backward**: every traceability row maps to a real code site.

Both directions only range over the **annotated** set. An
unannotated soundness-critical step (the Rabinowitsch encoding)
is invisible to both checks. The audit answered "are the proofs
we cite real?" (yes) but not "have we cited a proof for every
step that needs one?" (no).

## How the fix (Item 14) will also close the proof gap

The fix is not only to change the code but to **move the boundary
so the bug class cannot recur**:

1. **Model the disequality encoding in Lean.** Add a theorem
   stating the soundness obligation explicitly:
   `refute(F, diff≠0)` is sound iff `diff` reduces to 0 modulo
   `⟨F⟩` (ideal membership), OR `diff` is provably a unit. This
   theorem will *fail to prove* the unconditional Rabinowitsch
   step — which is the point: it forces the implementation to use
   only the sound refutation (ideal-membership / vanishing), or
   to discharge an `IsUnit` side-condition.
2. **Enforce the single-width assumption in code.** Replace the
   `bw >= bitwidth` absorb with a real consistency check
   (reject width-changing casts of arithmetic, per the committed
   Bug A guard), so the documented ASSUMES is actually
   maintained.
3. **Add a coverage check to the traceability tooling**: every
   `(dis)equality push` and every refutation conclusion in
   `try_algebraic_solve` must carry a `// PROOF:` annotation;
   fail CI on an unannotated soundness-critical step. This
   converts the silent gap into a visible, checkable obligation.

## Bottom line

The formal development is genuinely valuable and genuinely sound
*for what it covers*: the Gröbner engine, the 2-trick, the
equality encoding. The bugs are not in the proofs; they are in
the **unverified seam between the SMT query and the polynomial
system** — exactly the encoding/front-end layer that is easy to
treat as "obviously fine" and therefore easy to leave
un-mechanised. The corrective is to (a) shrink that seam by
mechanising the disequality encoding, (b) enforce the
width assumption the proofs depend on, and (c) make
"every soundness-critical step is annotated" a checked invariant
rather than an aspiration.
